Here's How I'd Cut a Runaway Snowflake Bill

A field guide to the five places Snowflake spend actually leaks — and what to check first.

2026.08.01 — InferReach

Every "our Snowflake bill tripled" story I've seen starts the same way: nobody altered anything on purpose. Usage just crept. Warehouses got bigger because someone was in a hurry. A dashboard got popular. A dbt job started running hourly instead of daily. Six months later, finance asks why the data team's AWS-adjacent line item is bigger than the data team's payroll.

The good news: Snowflake cost problems are almost always structural, not mysterious. You don't need to guess — you need to look in five specific places, in this order.

1. Start with WAREHOUSE_METERING_HISTORY, not the invoice

The billing dashboard tells you that you spent money. It won't tell you why. The first move is always:

select
  warehouse_name,
  date_trunc('day', start_time) as day,
  sum(credits_used) as credits
from snowflake.account_usage.warehouse_metering_history
where start_time >= dateadd('day', -30, current_date)
group by 1, 2
order by credits desc;

This alone usually explains 60-70% of a spend spike. In most audits I see one of two patterns: either one warehouse is doing 80% of the burn (concentration problem, easy fix), or spend is spread evenly across ten warehouses that all sit idle most of the day (sizing problem, different fix). You need to know which one you have before you touch anything.

2. Auto-suspend is set wrong almost everywhere

Snowflake bills per-second once a warehouse is running, but it doesn't shut off by default the way people assume. The default auto-suspend is often left at 10 minutes, or worse, someone bumped it to an hour "to avoid cold-start latency" and never revisited it.

That sounds trivial. It isn't. A warehouse that idles for 10 extra minutes after every query, run 200 times a day, is 33 hours of pure waste a day on that warehouse alone. For an interactive BI warehouse serving dashboards, I set auto-suspend to 60 seconds as a default and only raise it if I can show cold-start latency is actually hurting someone. For batch/ETL warehouses, auto-suspend should almost always be immediate — there's no user waiting on it.

alter warehouse analytics_wh set auto_suspend = 60;

This one setting, applied account-wide, is routinely the single highest-leverage change available — and it takes five minutes.

3. Warehouse sizing is usually guessed, not measured

People size warehouses the way they'd size a t-shirt — "this job feels big, give it an XL." But Snowflake credit cost doubles with every size step (X-Small → Small → Medium...), so an oversized warehouse doesn't just cost more, it costs exponentially more for workloads that don't actually parallelize well.

The tell is in query profile: if a query on a Large warehouse shows most of its time in a single non-parallelizable step (a big single JOIN, a window function over an unpartitioned dataset), throwing more compute at it doesn't help — you're paying 4x for maybe 1.3x the speed. I look at QUERY_HISTORY for the actual bytes scanned and execution time relative to warehouse size, and downsize anything where the marginal speed gain doesn't justify the credit jump.

select
  warehouse_size,
  count(*) as query_count,
  avg(execution_time)/1000 as avg_sec,
  avg(bytes_scanned) as avg_bytes
from snowflake.account_usage.query_history
where start_time >= dateadd('day', -14, current_date)
group by 1;

4. Workload isolation — the "one warehouse for everything" trap

A very common anti-pattern: one warehouse serves dbt runs, ad-hoc analyst queries, and the BI tool's dashboard refreshes. This feels efficient (one thing to manage) but is almost always more expensive, because:

  • The warehouse has to be sized for the worst workload, so every workload pays that price
  • A heavy analyst query queues behind (or competes with) scheduled jobs, so people bump the size "to be safe" — permanently, for a problem that only happens sometimes
  • You lose the ability to auto-suspend aggressively, because something is always about to run

Splitting into 2-3 purpose-sized warehouses (e.g. a small always-on BI warehouse, a larger batch warehouse that only spins up for scheduled transforms, and an ad-hoc warehouse analysts opt into) routinely costs less in total credits than one shared warehouse sized for the peak case, while also fixing the queueing complaints that got you into oversizing in the first place.

5. The quiet one: storage and query patterns compound over time

Compute gets the attention because it's the biggest line item, but two smaller leaks add up:

  • Time Travel and Fail-safe retention set to the max (90 days) on tables that don't need it — this multiplies storage cost for no operational benefit on staging/intermediate tables. Dropping retention to 1 day on ephemeral dbt intermediate models is free money.
  • select * habits in dbt models and BI extracts — scanning full-width tables when only a handful of columns are used inflates bytes scanned, which inflates both time and (on certain query patterns) cost. This is a code-review fix, not an infra fix, which is exactly why it never gets caught — nobody's job is to notice it.

What I'd actually do first, in order

If I inherited a Snowflake account with a bill that's grown faster than the business, this is the order of operations, because it's ranked by effort-to-impact:

  1. Pull 30 days of WAREHOUSE_METERING_HISTORY, find the concentration
  2. Fix auto-suspend account-wide (same day, near-zero risk)
  3. Split any "does everything" warehouse into purpose-sized ones
  4. Right-size based on actual query profiles, not vibes
  5. Fix retention settings on ephemeral tables
  6. Then go looking for query-level optimization, because by this point you're optimizing the remaining 20%, not the easy 80%

Most of this is a few days of work, not a re-architecture. The account structure is usually fine — it's just never been looked at with actual usage data since the day someone provisioned it.
